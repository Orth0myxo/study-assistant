# Master code-to-UX traceability

This table follows user-visible actions through the mobile component, HTTP contract, backend handler/service and resulting storage. “None” means no write/read on that action; it does not mean the surrounding screen has no state.

| User action | Mobile screen | Frontend function | API endpoint | Backend service | Database/storage | Result |
|---|---|---|---|---|---|---|
| Open Home / check backend | Home (`mobile/app/index.tsx`) | `fetchStatus()` -> `getHealth()` | `GET /health` | `api/health.py:health`; settings inspection | None | Shows configured/degraded status and limits. `reachable` is not proof of live Gemini call. |
| First authenticated request / bootstrap device | Usually Home history; any data call | `ensureUserToken()` -> `registerUserToken()` | `POST /api/v1/users` | `api/users.py:register_user` -> `UserStore.create()` | Adds `users` row with token hash; token stored in Expo SecureStore | Anonymous per-install owner ID/token. No login/account screen. |
| View recent legacy studies | Home | `loadRecent()` -> `listStudyJobs()` | `GET /api/v1/study-jobs?limit=20` | `api/study.py:list_study_jobs` -> `JobStore.list_for_owner`, source availability check | Reads owner-filtered `study_jobs` and `documents` | Recent saved jobs, empty state or error; topic-source sessions are excluded. |
| Start normal study | Home -> Upload | Home route to `/upload`; `pickAndUpload()` | `GET /health` sometimes for limit, then upload | Health route then document handler | No DB on health | Shows configured upload limit/idle selection. |
| Choose and upload PDF/DOCX | Upload | `pickAndUpload()` -> `uploadAsset()` -> `uploadDocument()` | `POST /api/v1/documents` multipart `file` | `api/documents.py:upload_document` -> `parse_document()` -> PDF/DOCX parser and OCR | Writes source bytes and `documents` row with extracted section JSON/owner | Extraction summary, warning(s), retryable error, or no-text state. |

| Edit/add/remove topics and re-review | Photo Topics | `editTopic`, `addTopic`, `removeTopic`, `runReview()` | `PATCH /topic-sources/{id}` then `POST /topic-sources/{id}/topic-review` | `update_topic_source()` then segmentation/matching | Updates saved topic JSON; review reads doc/source state | Validated 1–20 topics, max 200 chars each in client config; refreshed review. |

## Cross-cutting mobile-to-server behavior

1. `apiClient.ts:send()` resolves base URL, ensures Bearer identity for data routes, adds request ID, selects fetch implementation and applies operation timeout.
2. Multipart document/image requests use `FormData`; preview and example env enable React Native fetch due to Expo SDK multipart file-part compatibility note.
3. JSON DTOs in `mobile/types/api.ts` mirror Pydantic schemas in `backend/app/schemas/`. TypeScript checks this client's shape at compile time but cannot guarantee deployed server version matches.
4. The shared error envelope is converted to `ApiError`; screen-level recovery is deliberately limited to retry, reload, polling, or original-passage fallback as listed above.

## Product boundary summary

The existing export/history path is attached to `study_jobs`; the photo/topic flow attaches to `topic_sources` and computes output without creating a job. Likewise, source-note labels answer “which jottings/photo mentioned this topic,” whereas matched passages answer “which source-document section grounds it.” Future changes should preserve this distinction when evaluating API and screen behavior.
